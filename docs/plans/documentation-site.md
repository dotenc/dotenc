# Documentation site proposal

Researched 2026-09-24. Implemented on the documentation branch on 2026-09-25;
publication and the skill/plugin link release remain pending PR review.

Implementation uses an explicit list of canonical provider/security sources in
`docs-site/scripts/sources.ts`, generating their site views without moving the
original files. README guidance now lives in `docs-site/src/content/docs/`.
The CLI reference is generated from actual help, and the site exports Markdown
plus `llms.txt`. See `docs-site/README.md` for current maintenance commands.

The original research and migration rationale follow.

## Recommendation

Use Astro Starlight for public product documentation at `https://dotenc.org/docs/`.
Keep the existing marketing homepage and combine both static builds into the
existing GitHub Pages deployment. Prefer Markdown; use MDX only when a component
materially improves the explanation. Start with documentation for the latest
published CLI and explicit minimum-version notes for newer features.

This recommendation prioritizes static hosting, local search, readable source,
low operating overhead, and preserving the current brand. It is based on source
inspection and official framework documentation, not a performance benchmark or
a locally validated prototype.

## Current repository and skill evidence

- `README.md` is a symlink to `cli/README.md`: 1,108 lines and approximately
  6,600 words. A rewrite affects both the repository and CLI package introduction.
- `website/` uses Bun, Tailwind, static HTML, and vanilla JavaScript. Its existing
  build fingerprints assets and clears `website/dist` before writing output.
- `.github/workflows/deploy-website.yml` already uploads `website/dist` to GitHub
  Pages. Its push filter currently only watches `website/**`.
- `website/public/CNAME` contains `dotenc.org`. The homepage documentation CTA
  currently points to the GitHub README.
- `docs/` mixes public guides, implementation plans, and operational evidence.
  Public documentation needs an explicit content collection, not a blanket import.
- `SECURITY.md` is the detailed security specification and reporting entry point.
  Keep it authoritative and link to it or generate its public presentation from
  that source instead of maintaining a second independent specification.
- Inspected `dotenc/skills` at commit
  `2abc71e5bf04b5314b942ad50f529c293bbcbeb5`. The canonical skill is
  `skills/dotenc/SKILL.md`; the plugin copy is generated by `bun run build`.
  Both contain operating instructions and command tables. They do not simply
  delegate all behavior to the README. Their external references include
  `https://dotenc.org/#installation`, the README's `#provider-runbooks` anchor,
  and `docs/EXPO_EAS.md` on GitHub.

## Framework comparison

| Framework | GitHub Pages and search | Fit for dotenc |
| --- | --- | --- |
| **Astro Starlight** | Static output; official Astro Pages deployment guide; Pagefind search enabled by default. | Recommended. Documentation UI, Markdown/MDX, code presentation, and localization support without adopting a React or Vue application architecture. Versioned documentation is available through a community plugin. |
| **VitePress** | Official Pages deployment guide; built-in local search can be enabled. | Strong runner-up for a lean Markdown site. Vue is useful for custom interactive components. Prefer it if its authoring and default theme appeal more than Starlight's. |
| **Docusaurus** | Static Pages deployment; official Algolia integration; local search uses community plugins. | Prefer if maintaining multiple released documentation versions becomes a core requirement: versioning is built in. React/MDX and additional search choices are more machinery than this initial migration needs. |
| **Fumadocs** | Static builds supported with framework configuration; built-in search needs its static-index configuration. | Good when docs should share a React application stack or need extensive custom UI. Its default server-first approach adds decisions that the current static website does not need. |

The ranking reflects this repository's needs, not universal framework quality.
No framework requires moving hosting away from GitHub Pages.

## Proposed content structure

| Section | Content to extract or consolidate |
| --- | --- |
| Start here | Installation, quick start, existing-clone setup, first encrypted environment |
| Everyday use | Edit and rename environments, development profiles, run commands, precedence, Git diffs, monorepos |
| Teams and keys | Identity, supported keys, passphrases, 1Password, grants, revocation, complete offboarding |
| CI/CD | Bootstrap identity, GitHub Actions, redacted PR diffs, individual provider runbooks, OCI/build tools |
| Integrations | VS Code, agent skill and plugin, prerequisites, installation links |
| Reference | Commands, flags, configuration/environment variables, JSON interfaces and exit semantics |
| Troubleshooting | Doctor, deployment artifact scanning, common failures and recovery |
| Security | Short model overview, limitations, link to authoritative SECURITY.md and reporting instructions |

Keep the README focused on the product, demo, installation, three-command quick
start, essential security caveats, and direct links to documentation and support.
Aim for roughly 150–250 lines; preserve compatibility anchors where needed.

## GitHub Pages integration

1. Add a `docs-site/` Bun workspace with a dedicated public content collection.
   Keep repository plans and audit evidence outside that collection.
2. Build Starlight for `site: 'https://dotenc.org'` and `base: '/docs'`.
   This base represents its mount within the combined site. A deployment under
   a GitHub project URL instead would need the repository prefix as well.
3. Build the marketing site first, then copy the docs output to
   `website/dist/docs/`. Keep one upload and one deployment: a separate Pages
   deployment for the same repository would replace the existing artifact.
4. Keep the root CNAME, installer, assets, and existing homepage anchors intact.
   Test docs assets, search-index paths, trailing slashes, deep links, and the
   combined site's 404 behavior under the actual `/docs/` mount.
5. Expand deployment and PR validation triggers to include the docs workspace,
   imported content, root manifest/lockfile, and the deployment workflow itself.
   Install from the root using `bun install --frozen-lockfile`; retain pinned
   Actions and audit the expanded root lockfile.
6. Reuse current logo, typography, and blue/mint palette through scoped docs
   styling. Validate mobile layout, keyboard navigation, contrast, and search.

`docs.dotenc.org` remains a valid alternative if independent deployment is
desired, but would require a separate Pages site/repository and domain setup.
The proposed `/docs/` layout can use the existing domain and deployment.

## Skill impact and compatibility

No immediate skill change is required if existing URLs and anchors remain valid.
However, do not assume an agent that reads the README will automatically follow
every new documentation link.

After publishing the docs, update the canonical skill in `dotenc/skills` with a
small documentation lookup section: docs index, command reference, agent-safe
JSON editing, diagnostics, and provider runbooks. Fetch only the relevant page;
check the installed CLI version and use local help before relying on new flags.
Retain the bundled safety and secret-handling instructions for offline use.

Update direct provider links and regenerate the plugin with `bun run build`;
run the skills repository's `bun run check` and `bun run test`, plus relevant
behavioral validation. Do not edit generated plugin files or installed caches
as the source of truth. Follow that repository's release process for distribution.

Keep a compact `## Provider runbooks` section in the shortened README and retain
old GitHub guide paths as compatibility stubs when moving their content. GitHub
README anchors cannot be repaired with website redirects. Inventory other
inbound anchors before removing sections.

Make public pages readable as static HTML and expose stable Markdown source
links. An optional generated `llms.txt` index can improve discovery, but is not
required and does not guarantee that tools will follow links. Avoid handwritten
copies of documentation in skills or a second full-content AI document.

## Migration sequence and acceptance

1. Prototype Starlight with quick start, one command page, and the Expo runbook.
   Prove the combined artifact and local search at `/docs/` before migrating all
   content. No production change is needed for this check.
2. Move public content with one canonical source per topic. Check examples against
   the published CLI; keep unreleased implementation plans out of user guidance.
3. Add compatibility links, shorten the shared README, update homepage/docs links,
   and adjust repository guidance to reflect the new canonical documentation.
4. Publish the site, verify actual deep links and search, then release skill link
   updates. Existing skills should continue working throughout the transition.

Acceptance: reproducible frozen-lockfile build; working static pages and search;
no server dependency; intact homepage and installer; working legacy guide links
and inventoried README anchors; GitHub/npm-readable README; clear security
guarantees; no independently maintained duplicate reference; reviewed mobile and
keyboard behavior. Run the existing website build/tests and root lint when the
website changes, alongside the future docs build and link checks.
